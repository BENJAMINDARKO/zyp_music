## Critical Issues to Fix

### 1. High-Frequency Polling Causing UI Overhead
`PlayerProvider._startPolling()` (presentation/providers/player_provider.dart:297-310) fires `notifyListeners()` every **300ms** via `Timer.periodic`, **plus** position/duration stream listeners that also trigger. This causes ~3 forced rebuilds/sec even when nothing changes.

Use the streams directly with a debounce, or listen to `playerStateStream` instead.

### 2. HTTP Client Not Closed
`MusicAudioHandler.resolveRedirects()` (service/audio_handler.dart:61) creates `http.Client()` but never closes it — **memory leak** on every redirect resolution.

### 3. Response Body Drained on Redirects
`NetworkUtils.resolveRedirects()` (core/utils/network_utils.dart:18) calls `resp.stream.drain()` for 3xx responses. Redirect responses have no body — just close the response.

### 4. Sequential Pre-Downloads
`DownloadProvider.preDownloadUpcoming()` (presentation/providers/download_provider.dart:96) awaits each track download sequentially. For `prebufferCount=3`, 3 sequential HTTP downloads block queuing. Use `Future.wait` or batch.

### 5. Database Race Condition on Init
`PlaylistDatabase._database` (data/datasources/local/playlist_database.dart:9-13) has a TOCTOU race: two concurrent accesses while uninitialized will both call `_initDatabase()`. Guard with a latch/completer.

### 6. No Index on `downloaded_tracks.playlistId`
Table created at `playlist_database.dart:30-39`. Queries filtering by `playlistId` (e.g. `getDownloadedFilePaths`, `removeDownloadedPlaylist`) will be **full table scans** at scale.

## Estimated Impact if Unaddressed

| Issue | Severity | Impact |
|---|---|---|
| 300ms polling | High | Battery drain + jank on lower-end devices |
| HTTP client leak | High | OOM over long sessions |
| DB race | Medium | Crash on rapid playlist loads |
| Sequential downloads | Medium | Slow queue buildup |
